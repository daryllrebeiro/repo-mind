# Implementation Plan — Project Analysis Reports

Goal: `repomind report <repo>` produces a self-contained markdown analysis document per repository, generated **only from indexed graph facts** — never invented. Every claim traces to a query result; every diagram renders from real dependencies.

---

## Report structure (target output)

```markdown
# Analysis: <repo-name>
_Generated by RepoMind <version> on <date> — commit <sha if available>_

## 1. Overview
modules, source files, types, test ratio, build system(s)

## 2. Architecture
### 2.1 Module diagram (Mermaid)
### 2.2 Layer/package dependency diagram (Mermaid)
Narrative: entry points, layering style, detected stereotypes (@Controller/@Service/@Repository counts)

## 3. Key Flows
One subsection per detected flow (see Flow Detection):
flow diagram + participant list + confidence notes

## 4. Hotspots
Top-N symbols by impact score, with signal evidence tables

## 5. Points of Improvement
Signal-derived, each with evidence link:
- untested public API (public + zero affected tests)
- god classes (fan-out/fan-in above thresholds)
- config coupling (types binding many properties)
- missing architecture rules for detected stereotypes
- possible-vs-confirmed call ratio (resolution quality per package)

## 6. Code Smells & Risk Findings
Deterministic smell detectors over the graph (see Smell Detectors)

## 7. Appendix
Query transcript summary, engine version, unresolved-symbol rate
```

All diagrams are **Mermaid fenced blocks** so they render on GitHub/VS Code with zero tooling.

---

## Workstreams

### W1 — Mermaid emitters (`core/report`)
- `moduleDiagram()`: modules as nodes, DEPENDS_ON-style edges from cross-module imports
- `packageDiagram()`: packages as nodes; edge weight = edge count; prune below threshold to keep diagrams readable; cap nodes (top 30 by edge weight) with truncation note
- `flowDiagram(participants)`: linear/chained CALLS paths rendered left-to-right
- Tests: snapshot-style assertions on small graphs; node-cap behavior

### W2 — Flow detection
- Entry points: types with Spring Web annotations (`@RestController`, `@Controller`) or main classes (`@SpringBootApplication`)
- For each entry point: forward CALLS traversal (depth ≤ 6), collect the path skeleton controller→…→leaf
- Group flows sharing ≥70% of participants; emit top 15 flows by depth×breadth
- Confidence: CONFIRMED-only paths rendered solid; POSSIBLE edges dashed with legend note

### W3 — Smell & risk detectors (deterministic, evidence-backed)
| Detector | Signal | Evidence emitted |
|---|---|---|
| God class (fan-out) | outgoing CALLS > 20 | count + top targets |
| God class (fan-in) | direct callers > 15 | caller list sample |
| Untested critical | impact ≥ HIGH ∧ affectedTests = 0 | score breakdown |
| Cyclic package deps | SCC over package graph | cycle members |
| Config hotspots | type bound to > 15 property keys | key sample |
| Dead-ish code | public type with 0 incoming structural edges ∧ not entry point ∧ not test | fqn list |
| Layer skips | controller→repository edges (uses rules engine) | violation rows |

Vulnerability posture in v1 is **structural only** (e.g., `@CrossOrigin("*")` presence, `System.exit` usage, raw `Runtime.exec` calls found during parsing). Real CVE/SAST scanning is explicitly out of scope and will be stated as such in every report.

### W4 — Report assembly + CLI/MCP
- `core/report`: `ReportGenerator(dbPath, repoRoot): String` — pure assembly from `RepoQueryEngine`; no re-parsing
- CLI: `repomind report <repo> [-o out.md]` (default `<repo>/.repomind/report.md`)
- MCP tool: `generate_report` returning the same markdown (capped preview + file path)
- Determinism: same index → byte-identical report (timestamps only via explicit flag)

### W5 — Validation on example repos
Run against `java-examples-for-repo-mind/{spring-petclinic, piggymetrics, gs-rest-service}`:
1. `index` → measure unresolved-symbol rate (Phase 2 gate)
2. classpath resolution needs Maven on PATH — install Apache Maven latest
3. Generate reports; manually verify diagrams render and claims match reality
4. Feed discrepancies back as detector/eval-harness fixes

---

## Execution order
1. W1 emitters (+tests) → 2. W4 skeleton (overview+hotspots+appendix) → 3. W3 detectors → 4. W2 flows → 5. W5 validation pass → 6. MCP tool wiring

Non-goals: LLM-written narrative prose (all text is template + data), vulnerability scanning beyond structural markers, cross-repo analysis.
